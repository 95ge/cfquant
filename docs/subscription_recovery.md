# 账号订阅续订与行情拥塞隔离

本修复处理“后台账号续订超时，主动拆掉整个交易实例连接”的连锁故障，并减少正常续订的重复日志。

## 故障边界

`XtQuantTrader` 为恢复 QMT / Web 重启后丢失的账号回调注册，每隔约 2 秒续订一次。此前续订的 `CfquantTimeout` 等异常可能触发 `_rebuild_connection()`，关闭该交易实例的所有 RPC 客户端。在途查询因此会收到 `cfquant client closed`，其他账号也可能被牵连。

SDK 等待响应超时只表示确认未及时到达，不能证明连接已经断开。行情堆积、QMT 调度繁忙和传输断连需要分别处理。Web 内部订阅请求超时也不应单独成为交易通道进入 30 秒冷却的依据。

交易实例关闭的是其自身持有的客户端，不会直接关闭独立的 `xtdata` 默认客户端。不过，Web 到 QMT 的连接可能同时承载行情事件与交易响应，因此底层连接本身仍可能受行情拥塞影响。

## 修复后的行为

| 情况 | 处理 |
| --- | --- |
| 正常续订成功 | 保持约 2 秒巡检；已有注册只刷新路由，不重复调用 QMT `set_account`，不输出每轮排队、订阅成功及响应完成日志。 |
| 续订超时或拒绝 | 保留所有客户端、在途请求及回调处理器；按账号记录错误，下一次尝试的最短等待依次为 2、4、8、16、30 秒，之后最多 30 秒。实际尝试还受巡检周期和请求耗时影响。 |
| 持续续订失败 | 每个账号首次失败记一条警告，此后最多每 30 秒一条；错误请求 ID 变化不会导致每轮重复打印。 |
| 续订恢复 | 清除该账号的退避状态，记一条恢复日志，恢复正常巡检间隔。 |
| 底层连接实际断开 | 由对应传输客户端的接收循环及 `start()` 重连；后续续订恢复远端注册，不调用整个交易实例的重建。 |
| QMT 重启或远端注册丢失 | 即使请求带有续订标记，只要本地注册不存在，仍完整初始化账号并登记回调。 |
| 初次初始化失败 | 回滚本次新增路由，确保下一次续订仍会执行完整初始化。 |
| Web 内部 `xttrader.subscribe` 超时 | 返回超时，不因这一次超时将交易通道标记为冷却；其他请求及真实断连处理仍按原规则执行。 |

首次显式订阅和错误日志保留。显式 `connect()` 的失败重试仍可重建交易实例连接。恢复流程只重试幂等的账号订阅，不重放委托或撤单。

初始化仍先安装回调路由，再调用 QMT 原生方法，以接住原生初始化期间同步到达的回调。

## 更新范围

需要同步更新外部 Python SDK、Web 服务和 QMT 桥接代码，并在合适的维护时段重新加载相关进程。仅更新其中一层，无法同时获得连接隔离和日志降噪。

- SDK：`cfquant/xttrader.py`。
- Web：`cfquant_web_server.py`。
- QMT 共用实现：`cfquant/tx_trade_bridge.py`、`cfquant/normal_bridge.py`。
- Lite 独立入口：`CFQUANT_LITE.py`、`CFQUANT_LITE_SH.py`、`CFQUANT_LITE_SZ.py`，通过同步工具生成，保留 GBK 编码及独立部署能力。

源码更新后可运行 `python tools/sync_qmt_release.py --check --no-cache` 校验三个 Lite 入口。

## 验证与限制

回归用例覆盖 Pipe、LTtx、Web 三种客户端：连续续订超时时保留在途查询和其他账号的回调；实际断连后自动恢复；远端注册消失后的重新登记；按账号退避及日志限频；QMT 桥接及三个 Lite 入口的幂等续订、首次初始化和独立部署。

该修复没有提高行情链路的持续处理能力，也没有扩大 `OrderedSender` 缓冲区。真实发送队列溢出仍会断开受影响的底层连接；若行情和交易共享该连接，相关请求仍可能失败。它阻止的是“续订未及时确认，再主动关闭整个交易实例”的额外故障扩散。

持续全推过载还需要结合队列积压和消费速度，另行处理行情吞吐与传输连接隔离。外部网关若将 `subscribe_whole_quote` 的异常直接传播出 `connect()`，也需要在网关侧捕获异常、报告行情不可用并安排恢复；本仓库未包含该网关的实现，不能据此认定其子进程退出问题已完全解决。

本地模拟回归不代表已经完成实盘全推压力验证。
