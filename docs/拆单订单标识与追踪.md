# 拆单订单标识与追踪

一次 `XtQuantTrader.order_stock` 调用可能在 QMT 或柜台侧产生多笔真实委托。cfquant 不应把这些子单合并为一个 `order_id`，也不会为了添加追踪信息而额外发送委托或改变提交数量。

## 字段含义

| 字段 | 含义 |
| --- | --- |
| `order_remark` | 用户填写的投资备注，按原文返回。 |
| `cfquant_order_remark` | 发送到 QMT 的完整备注：原备注加 `__cfq_<32 位 UUID>`。标识一次提交，可以被多个下游子单共享。 |
| `cfquant_submission_id` | 从原生备注提取的 32 位 UUID，用于关联同一次提交。 |
| `order_id` | 当前真实子单的标准订单号；按此号码查询或撤销该子单。 |
| `cfquant_child_id` | `<cfquant_submission_id>:<order_id>`，区分同一次提交中的真实子单。只有存在有效正整数标准订单号时才提供。 |

例如同一次提交产生两个子单，提交 ID 为 `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`：

| 子单 | 数量 | `cfquant_child_id` |
| --- | ---: | --- |
| `1098909568` | 100000 | `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa:1098909568` |
| `1098909569` | 12672 | `aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa:1098909569` |

新增字段出现在带有 cfquant 原生唯一备注的委托/成交查询、回调和批量提交结果中。手工委托或无法恢复该备注的历史记录可能没有这些字段，读取时应使用 `getattr` 或 `dict.get`。异步批量结果可包含提交 ID，真实订单号尚未确认时不生成子单 ID。单笔同步下单仍返回整数订单号，异步下单仍返回请求序号，保持原接口返回类型。

## 在提交时设置备注

如果策略主动拆成多次调用，可以给每次调用传入不同的 `order_remark`，例如 `rebalance_20261110:sell:01`、`rebalance_20261110:sell:02`。每次提交还会生成独立的原生 UUID。批量下单在未指定逐笔备注时已经使用“批次前缀 + 序号”；算法拆单使用“算法任务 ID + 子单序号”。用户可以在自己的任务记录中保存这些备注和所属任务。

如果只提交一次、由下游自动拆单，在调用 `passorder` 时还不知道每个真实子单，不能分别改写它们的原生投资备注。此时保留共同提交 ID，在查询与回报中用子单 ID 追踪。子单 ID 按真实订单号生成，不依赖回报先后顺序。

```python
# trader 和 account 使用已有连接；下列代码只查询。
for item in trader.query_stock_orders(account):
    print({
        "order_id": item.order_id,
        "volume": item.order_volume,
        "remark": item.order_remark,
        "submission_id": getattr(item, "cfquant_submission_id", None),
        "child_id": getattr(item, "cfquant_child_id", None),
    })

for item in trader.query_stock_trades(account):
    print({
        "order_id": item.order_id,
        "trade_id": item.traded_id,
        "volume": item.traded_volume,
        "submission_id": getattr(item, "cfquant_submission_id", None),
        "child_id": getattr(item, "cfquant_child_id", None),
    })
```

`cfquant_child_id` 是关联标签，不能代替 `order_id` 传给撤单接口，也不能代替成交号对多次成交去重。跨 QMT 进程的引用需要确认属于同一真实订单后才能归一化；共有备注、价格或数量本身都不足以证明这一点。子单标签由最终标准订单号派生，如果订单号之后通过已确认的跨进程映射发生变化，标签会随之更新。

## 修复范围与运行端更新

共享桥的元数据缓存会为共享提交备注的不同真实子单保留独立记录，委托与成交查询保留原生有效订单号。不同回调引用只有在匹配已记录的同子单柜台委托号或已验证引用时才允许归一化。没有子单证据的共享提交备注不会从多个已知子单中任意选择一个。

旧版本缓存中通过共享 UUID 合并的引用不再作为可靠别名使用；加载时保留提交信息和已有 canonical ID，其他子单通过后续原生查询/回报重新建立关联。这可能暂时使缺少备注及可靠引用的历史记录无法补齐策略信息，但不会因此覆盖其有效原生订单号。

旧备注补充路径和三份独立 LITE 入口也包含修复。运行端需要更新对应的共享桥或重新部署 LITE 入口并重启策略后才生效；只更新外部 SDK 不能修复旧 QMT 进程已经改写的返回值。已有绩效库或账本中的重复记录需要另行核对，本修复不会自动修改历史账本。
