# 订阅持久化与恢复设计草案

状态：2026-11-06；默认 Web 路径的 SQLite 清单、客户端租约、桥接幂等键和恢复限流已实现。显式 ctypes/LTtx 直连、定时器自动恢复和外部进程自身重启后的回调函数恢复仍不在当前实现范围。

## 目标与原则

外部 Python 程序仍在运行时，cfquant Web、通信服务或 QMT 重启后，可以恢复该程序当前仍需要的订阅；已经退出的程序不会因为数据库中存在历史记录而重新占用 QMT 资源。

SQLite 保存订阅意图，租约决定是否允许实际订阅。恢复必须同时满足：客户端在本次服务启动后完成确认、订阅仍在其当前清单中、未取消、路由有效、桥接端支持恢复协议、未超过资源上限。数据库中的旧 `active` 状态不能直接作为恢复依据。

分开处理四种状态：

- 订阅意图：需要哪类数据、参数、所属客户端和路由。
- 客户端存活：最近一次有效心跳、当前连接代次、租约。
- 上游资源：当前桥接代次、原生订阅 ID、实际创建和释放结果。
- 本地回调：外部 Python 进程中的函数对象及对应标识。

只持久化可校验的 JSON 参数和回调标识，不序列化 Python 函数、闭包、ContextInfo、连接对象，不使用 pickle。行情数据和历史交易事件不写入本订阅数据库。

## 当前代码基础

- `cfquant/xttrader.py` 已保存期望账号清单，并检查和补齐账号回调注册，可复用其幂等及取消语义。
- `cfquant/xtdata.py` 目前主要保存订阅 ID 与回调；`cfquant/quote_leases.py` 每 10 秒续租，但不处理服务端返回的缺失订阅。
- `cfquant/quote_service.py` 能在 Web 存活时恢复丢失的共享上游；外部客户的 Web 转发记录仍在内存中。
- `cfquant/qmt_inner.py` 和 `qmt_inner_runtime.py` 缺少会话恢复协议，原生会话、资源及回调注册保存在内存中。
- 已有 `AlgoStore` 使用 SQLite、WAL 和独占文件锁，可参考其单实例管理方式；算法任务是否恢复仍由算法引擎决定。

## 存储位置和职责

当前使用独立的 `runtime/db/subscriptions.sqlite3`，支持通过运行目录配置间接指定路径。数据库属于本地运行状态，不能打进公开发布包或提交到 Git。

独立 `SubscriptionStore` 管数据库事务，`SubscriptionManager` 管存活、恢复、取消及清理。Web 路由、行情服务、兼容交易接口、原生接口分别通过适配器接入。QMT 桥接仅维护内存登记、幂等键、租约和原生资源，不在 QMT 回调中操作 SQLite。

当前由 Web 进程独占管理该库，处理默认 `auto/web` 路径。PipeHub 仍负责转发数据，不同时打开同一数据库执行恢复。显式 `ctypes/lttx` 直连不会自动经过 Web；其持久化必须单独接入同一管理协议，不能仅改 Web 后就宣称直连也支持。完全不运行 Web 的独立部署需要明确的管理宿主；暂不增加第二套互不协调的恢复器。

SQLite 使用 WAL、短事务、单写入队列和有界忙等待；新增、取消、代次变更采用持久提交。网络调用和 QMT 调用始终在数据库事务之外。单实例锁拒绝两个管理器同时运行；同时下发管理器代次，桥接拒绝旧管理器的迟到指令。数据库故障时明确报告持久化失败，不把内存操作伪装成已获得重启恢复保障。

## 数据模型

| 表 | 主要字段 | 用途 |
| --- | --- | --- |
| `owners` | `id`、凭据摘要、客户端标识、最后确认时间、清单版本和摘要 | 区分调用方身份、进程实例及连接；恢复凭据仅存摘要 |
| `subscriptions` | 稳定逻辑 ID、owner、JSON 订阅参数、期望状态、原生 ID、桥接代次、恢复状态和退避字段 | 当前期望订阅、取消记录及原生资源绑定 |
| `meta` | `key`、`value` | 数据库恢复代次等元数据 |

当前实现将订阅意图和绑定压缩在 `subscriptions` 表中，后续需要审计历史或多阶段清单提交时再拆分独立 binding 表。

索引覆盖 owner、意图状态、到期时间和下一次重试时间。每次只分页扫描到期或待恢复数据，避免每次心跳全表扫描。

同一次创建请求始终携带相同逻辑 ID；同一 ID 与版本号的重试不插入新记录。用户主动重复调用订阅可以产生多个逻辑订阅，分别取消；只有语义完全一致、允许共享的订阅才复用上游资源。共享键必须包含桥接、账号/权限范围、数据类型、周期和复权等参数；原生 `follow` 参数还受当前 ContextInfo 影响，首期不跨原生会话合并。共享上游最后一个有效使用者退出后才释放。

## 两个期限：占用资源与允许恢复

以下是建议初值，均可配置，实施时需要按实际负载验证。

| 参数 | 建议初值 | 语义 |
| --- | --- | --- |
| SDK 心跳间隔 | 10 秒，带少量随机抖动 | 沿用现有全推心跳节奏；每个客户端批量续租 |
| 活跃租约 | 45 秒 | 延续现有全推资源回收习惯；超期加维护周期后停止投递并释放该客户端引用 |
| 可恢复记录保留 | 距最后有效客户端确认 24 小时 | 客户端离线时只保留描述，不保留上游订阅，不后台反复恢复 |
| 取消/过期记录保留 | 7 天 | 用于排查和拦截迟到请求；过期会话不能通过旧请求复活 |
| 过期维护 | 每 10 秒，最多处理 200 条 | 分批释放及清理，避免集中阻塞 |
| 每个 QMT 恢复速率 | 每秒最多 5 个原生资源操作，最多 1 个在途恢复 | 不占满原有 QMT 有序请求泵；租约刷新和只读探测另行批量处理 |
| 重试退避 | 1、2、4、8、16、30 秒，带抖动 | 每个订阅独立；桥接离线时按桥接探测，不逐个请求 |
| 连续恢复失败 | 10 次后暂停常规恢复 | 桥接恢复、客户端提交新清单或显式恢复时重新排队；重复心跳不重置失败次数 |

持续活跃的订阅不因创建时间超过 24 小时而过期。24 小时限制的是没有客户端确认的旧记录。

心跳只续已知且仍有效的逻辑订阅；心跳中未出现的 ID 不能直接当作取消，因为心跳可以分批。取消由明确指令或完整清单版本变更处理。

服务启动后所有外部 owner 都需要本次启动下的重新确认，不从磁盘上的租约时间直接判定存活。客户端重连必须完成新握手并提交最新清单，旧连接缓存中的心跳不能确认新会话。长期离线后若记录已删除，仍存活的 SDK 可用内存中的最新清单建立新会话；服务端不会自行从历史记录恢复。

运行期间用单调时钟判断租约。数据库时间用 UTC 保存，仅用于跨重启保留和清理；时钟回拨等异常不得延长旧记录的自动恢复资格，仍必须经过新握手。

## 恢复流程

1. 服务启动，生成新的启动标识，取得管理权；读取记录并标为等待客户端确认，不立即调用原生订阅函数。
2. SDK 在后台重连后重新握手，证明原 owner 身份，更新连接代次，并提交本地仍有效的完整订阅清单及清单版本。回调处理器先安装，再允许投递事件。
3. 服务端事务性核对清单。分页清单只有在全部收齐、校验数量/版本并提交后才生效；不完整上传不删除已有意图。数据库中存在、但新清单已经取消的记录进入释放流程。
4. 只为已确认且租约有效的 owner 安排恢复，先确认账号/桥接路由和权限仍然有效。账号绑定或权限已变化时暂停该记录，不自动转到其他账号或行情源。
5. 用逻辑订阅 ID、版本和桥接代次查询上游状态。资源仍存在时只更新归属代次及投递地址，不重复订阅；已确认不存在时才创建。
6. 创建成功后保存原生 ID 与代次映射，再确认恢复结果。若首包早于订阅应答，使用预先建立的逻辑事件路由接收；失效代次的旧事件丢弃。
7. 恢复后只接收后续行情和交易回调。资金、持仓、委托、成交等当前状态由查询核对；本机制不补发断线期间的历史事件。

一次恢复失败不阻塞其他客户端；同一 owner 的清单数量、待恢复队列、单次 RPC 大小和每个桥接的恢复速率都有上限。排队期间只有有效心跳继续续租，不因排队本身延长离线客户端的资源资格。

## 幂等与崩溃窗口

SQLite 与 QMT 原生调用不能组成一个原子事务，不能仅靠数据库唯一键承诺原生函数绝不重复执行。

- 先提交订阅意图，再发送带逻辑 ID 和版本的创建命令；桥接登记该键，重复命令返回同一结果。
- RPC 超时代表结果待核对；查询相同逻辑 ID 的桥接登记，禁止换新 ID 再创建。
- Web 在 QMT 已创建、数据库尚未记录结果时崩溃：重启后先按逻辑 ID 对账，再接管已有资源。
- QMT 整个进程重启时，旧进程原生资源已经消失，可在新桥接代次创建；只重载策略时，还必须由桥接生命周期清理、失效回调隔离和租约回收处理旧资源，不能仅靠 generation 变化假定原生资源已释放。
- 无法确认旧资源是否清理的桥接进入“结果待核对”，停止重复创建，展示原因。旧版桥接不支持逻辑 ID 查询和幂等登记时，不启用这项自动恢复能力。

## 取消和过期清理

取消先提交 `desired_state=cancelled` 并增加版本，再移除投递并释放上游。即使 QMT 暂时不可达，下一次启动也不得恢复已取消意图。接口区分“取消意图已持久保存”与“原生资源释放完成”；释放失败保持待清理状态。

恢复与取消竞争时，恢复结果必须核对最新版本；迟到的旧创建结果进入清理，不能把新取消覆盖为 active。重新订阅使用新逻辑 ID，避免旧退订误伤新资源。

租约过期后先停止向该 owner 投递，再释放它持有的共享引用；其他活跃客户端和内部算法引用不受影响。桥接暂不可达时保留待释放标记；托管资源还应在桥接端带有独立到期清理，避免 Web 长期退出后遗留原生订阅。管理器不能用自己的心跳替已经离线的外部 owner 永久续租。

删除取消记录必须满足上游已释放或旧进程已确认消失；对仍待清理的记录不能只因超过 7 天直接删除。该类异常数量也受上限约束，超过上限拒绝新增并提示处理，不能无限增长。过期凭据及未知的旧逻辑 ID 不能用心跳重新创建记录；新建需走当前会话下的显式创建协议，因此删除历史记录后也不会被旧请求复活。

## 数量和磁盘上限

建议首期默认：每个外部 owner 最多 512 个有效逻辑订阅，整个管理实例最多 5,000 个；有效 owner 最多 128 个，待恢复工作队列最多 2,000 个。每个 owner 的恢复列表采用分页公平调度，不因单个大客户占满队列。

这些上限约束的是逻辑记录数量。还需要单独限制请求参数字节数、证券列表大小、每个桥接原生资源数；单个“全市场”订阅不能因为只占一条记录就视为零成本。原生资源预算按数据类型和终端配置，不能把某一固定数量当作所有券商的安全容量。

记录总数建议最多 100,000 条。达到上限先清理已释放的到期历史；仍不足时拒绝新增并明确说明，不驱逐活跃订阅，也不删除尚未确认释放的记录。定期检查主库及 WAL 大小、checkpoint 和写入失败。历史清理采用小批删除；整理数据库在低负载时进行，不阻塞行情回调线程。

## 接口与兼容性

保留原有 `subscribe_quote`、`subscribe_whole_quote`、`unsubscribe_quote` 和交易回调注册名称。默认 Web 客户端已新增内部的会话握手、完整清单同步、批量心跳、状态查询协议；不是对所有历史 RPC 做重放。`XtQuantTrader` 账号回调继续使用原有独立的账号恢复线程，避免改变既有请求协议。

托管模式向调用方提供稳定逻辑订阅 ID，由 SDK/服务映射到本代原生 ID，重连后原句柄仍可取消。状态查询可以显示当前原生 ID，但它不能跨桥接重启使用。

`QmtInnerApi` 目前强调原生返回值语义，不能悄悄将原生 ID 改成逻辑 ID。建议首期通过会话级恢复选项显式启用托管模式，并在接口文档注明句柄语义；原生直通模式继续保持原始返回值，也明确不承诺订阅恢复。通用 `call()` 在托管模式中也必须走同一订阅管理入口，避免旁路。

SDK 必须保留当前订阅描述、回调对象和取消意图，并有独立于用户回调执行速度的后台心跳。离线期间本地取消应立即生效，重连提交的完整清单负责同步取消；需要再启动外部程序的场景由业务代码重新安装回调，数据库不会恢复已经退出的 Python 进程。

算法任务是内部 owner。其行情引用由任务引擎完成恢复核对后重新申请，不能依赖外部 SDK 的 45 秒租约，也不能由订阅数据库自行把已终止算法拉起。

自动恢复允许名单首期包括行情订阅和 `QmtInnerApi` 回调登记；`XtQuantTrader` 账号回调继续由既有独立恢复线程负责。下单、撤单、资金操作及其他具有业务副作用的调用不进入恢复清单。`schedule_run` 可能触发交易，首期不自动恢复；如后续支持，必须另行规定是否跳过错过的执行、截止时间、最大次数及任务取消语义。

## 验收场景与落地顺序

必须覆盖：

1. SDK 存活，分别重启 Web、通信服务、QMT，订阅和事件路由恢复且不重复投递。
2. Web 重启但 SDK 已退出，数据库记录不会产生新原生订阅。
3. SDK 突然退出，45 秒加维护周期后释放引用；共享使用者不受影响。
4. Web 停机期间 SDK 取消订阅，重连后取消优先于旧数据库 active 状态。
5. QMT 创建成功但应答丢失，以及 Web 在创建与记账之间崩溃，均先对账且不重复创建。
6. 恢复时取消、迟到应答、旧连接事件、原生 ID 重用均不误恢复或误取消新资源。
7. 分页清单传输中断不被当作大量取消；旧心跳不能覆盖新清单。
8. 超过保留窗口、数据库记录已清理，活着的 SDK 可以用最新清单建立新会话；旧凭据不能复活已取消记录。
9. 数百客户端同时重连时限流、公平调度、失败隔离有效；健康订阅不重复触发原生创建。
10. SQLite 忙、磁盘满、进程崩溃、双管理器启动及系统时钟调整有明确结果，不报告虚假的恢复成功。
11. 外部程序自身重启需重新注册回调；账号权限变化、旧版桥接、定时器不被擅自自动恢复。

实施顺序：先实现存储、状态机及隔离测试；再打通默认 Web 路径的 SDK 清单、行情、账号回调和原生托管模式；补齐桥接幂等、租约清理和 Lite 生成；最后单独覆盖显式直连的管理宿主及生命周期。各路径以能力协商和测试结果声明支持范围。

网页状态建议显示有效订阅、等待客户端确认、恢复中、等待桥接、暂停恢复、待清理及最后错误；明确区分描述记录数和实际原生资源数。提供按客户端清理和恢复操作，但“恢复”仍需有效客户端/内部任务确认，不能一键复活所有历史记录。
