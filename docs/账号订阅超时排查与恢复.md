# 账号订阅超时排查与恢复

`account callback subscription recovery failed ... cfquant request timeout: xttrader.subscribe`
表示 SDK 在等待账号订阅请求回包时超时。后面出现 `restored`，说明后续请求成功了；仅凭这两条日志，不能确认网络断开、订阅被删除或回调已经漏送。

## 为什么会反复超时

旧逻辑每轮间隔 2 秒发送一次 `xttrader.subscribe` 续订，回包等待预算也是 2 秒。已有登记的续订通常不会重复切换 QMT 账号，但仍然经过这些路径：

1. Web 按客户端和账号保序的业务队列。前面的慢查询会挡住同一账号的续订。
2. 普通 QMT 桥接的请求泵。原生调用必须留在对应执行线程，泵的时间片只在调用之间检查，无法中断正在阻塞的原生调用。
3. 共享传输上的响应与行情发送队列。大行情包、发送变慢或接收方处理能力不足，也可能延迟小回包。

因此，后台检查经常超时不一定表示账号订阅真的失效。它还可能反映业务队列或发送链路的拥堵；较短的检查预算会放大这类现象。单独增加超时时间不能解决这些排队来源。

## 本次修复

- SDK 先请求只读接口 `cfquant.account_subscription_status`，只有登记缺失时才发送真正的 `xttrader.subscribe`。检查不会切换账号、调用原生订阅或重放交易。
- Web 分别核对当前外部客户端的回调转发登记和上游 QMT 的登记。检查使用独立、有界的执行队列，避免被同客户端、同账号的业务请求挡住。真正的订阅、退订和交易保持原有业务队列顺序。
- 普通桥接在接收线程直接读取已完成初始化的订阅状态，继续执行托管策略的权限与代际检查。初始化中、已退订、其他客户端或其他账号类型的登记，不会被误报为有效。
- 默认后台回包等待预算从 2 秒调整为 5 秒；保留按账号退避和失败日志。检查超时不会额外发起重新订阅，也不会因此关闭健康连接或把交易通道标记为离线。
- 失败日志增加 `action`、`request_id`、`timeout` 和 RPC 时间信息；收到 Web 返回的错误时，还能看到 `web.queue_ms`。
- 旧 Web/QMT 明确返回“不支持接口”时，SDK 自动使用原来的续订协议，并在 60 秒后重新尝试能力检查。超时和账号模式未确认不会被当成“不支持接口”。

检查确认的是回调路由和初始化登记，不能证明 QMT 原生业务线程正在正常处理所有请求。高级模式的独立交易桥仍通过其交易轮询线程读取请求；它不具备普通桥接接收线程的绕过效果。共享发送队列拥堵、原生调用卡住整个解释器或 QMT 进程无响应，也仍可能造成超时。

## 更新与现场确认

需要更新客户端 SDK、运行 Web 的项目，以及 QMT 中实际运行的桥接策略。独立 Lite/SH/SZ 脚本已同步；只更新 Python 包而保留旧的 `.rzrk` 或旧策略进程，会走兼容续订路径，无法获得完整的排队改进。先在模拟环境重新部署并启动对应策略，再验证。

观察以下场景：

- 同账号慢查询期间，订阅检查能否保持成功。
- QMT 或 Web 重启后，账号回调能否自动恢复且没有重复派发。
- 明确退订后，不应被后台检查重新订阅。
- 行情高峰时，如仍有超时，记录对应 `request_id`、RPC 的 `connect_send_ms`/`response_wait_ms`、Web 排队时间、桥接请求队列和发送队列状态。

没有收到响应时，客户端无法获知该次请求在 Web/QMT 内部的准确耗时；不要将缺失的耗时当作零。发送队列的 `buffered_bytes`、`oldest_age_ms` 持续增长更支持发送拥堵；请求队列增长且原生执行时间变长更支持 QMT 业务调用阻塞。应结合客户当时的请求量、订阅范围及完整日志判断，不能仅由交替出现的超时与恢复日志锁定原因。
