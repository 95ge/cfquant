# 策略停止与管道线程清理

## 问题与原因

旧实现中，停止 `CFQUANT_LITE.py` 后可能继续出现“命名管道连接或读取中断 / connect named pipe timeout”日志。后台线程设置 `daemon=True` 仅影响 Python 进程退出，不会随着 QMT 策略停止而自动结束。

影响停止的具体路径包括：

- 策略先取消 QMT 定时器、清理行情订阅，再关闭通信；前面的原生调用或调度锁阻塞时，管道客户端仍会重连。
- 连接等待、重连间隔和满队列写入缺少可中断的停止检查。
- 收发连接尚在握手时未保存到客户端，停止操作无法立即关闭它们。
- 对同一客户端再次调用 `start()` 会清除停止事件，使尚未退出的旧线程继续运行。

## 本次处理

策略入口先关闭普通桥接和交易桥接的通信，再进行 QMT 定时器与行情订阅清理。手动导入与自动管理的策略均使用这一停止流程。

连接等待和重连间隔响应停止事件，接收队列满时定期检查停止状态。关闭操作会关闭正在握手及已连接的管道、唤醒接收线程，并在限定时间内等待连接、心跳和发送线程退出。

关闭后的桥接和管道客户端不可复用；策略重新加载时创建新实例。迟到的策略回调不会重新启动已关闭的桥接。三个独立 Lite 脚本与公共 Pipe 实现保持同步，生成工具也会保留这些修改。

## 生效与验证范围

Lite 使用内嵌实现，升级 Python 包后仍需要更新 QMT 中实际加载的 `CFQUANT_LITE.py`（或 SH/SZ 版本）。已经由旧代码创建的残留线程不会被替换磁盘文件自动修复；若旧策略停止后仍有残留，应在完成更新后重启对应 QMT 进程。

回归覆盖缺失管道、握手阻塞、满接收队列、长重连间隔、重复停止、迟到回调、原生清理阻塞和清理失败重试；Windows 测试使用随机独立管道验证阻塞读写的中断，不连接用户的 QMT 或 Hub。

此修复依赖 QMT 调用策略停止入口，不能强制终止已经进入 QMT 原生接口的业务调用。如果 QMT 清理调用仍然卡住，通信会先停止，但原生清理本身仍需返回。自动管理功能重新创建策略属于另一次启动，应结合自动运行设置和实例信息区分。
