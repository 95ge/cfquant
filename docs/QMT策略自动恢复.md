# QMT 策略自动恢复

当 QMT 主进程仍在、托管策略却因异常停止时，cfquant 每 20 秒检查一次当前绑定模型。确认停止且自动恢复接口可用后，直接调用 QMT 的 `CStrategyTradeManager::runStrategy`。检查使用内存中的模型配置和 `isFomrulaRun`，不使用鼠标、键盘或窗口坐标，也不重启整个终端。

## 生效范围

- 绑定已启用，且开启“自动导入策略”和“策略自动运行”。关闭策略自动运行后，恢复检测不会启动模型。因此，需要手动停策略进行调试时，应先关闭该选项。
- 仅处理当前绑定模式、当前目录及当前部署代次的托管策略；不会启动历史模式或其他用户策略。高级模式、独立市场按部署任务中的角色分别匹配。
- 启动前核对策略名称、模型 ID、资金账号、账号 Key、运行方式、主图品种、周期及自动运行开关。重名、字段不符、导入尚未完成、绑定已改变均不启动。
- QMT 必须已经登录。登录中的终端等待下一轮检测；自动登录仍由原来的登录服务负责。
- 不按券商、QMT 版本号或 DLL 整文件哈希放行。运行检测按实际加载模块中所需的导出接口判断；目前适配 Qt 5、MSVC x64 ABI，其他架构或 Qt 主版本需要对应适配。策略检测不依赖自动登录模块，也不再限定 Qt 5.6.2 这一小版本；自动登录维持自身的兼容性校验。
- 运行检测、自动启动、白名单就绪查询、弹窗读取和弹窗关闭分别报告能力。旧版本缺少 `isConnWhiteListReady` 时仍可调用其原生 `runStrategy` 启动策略，状态中 `can_check_whitelist=false`、就绪结果为未知，不视为白名单已经就绪。缺少 `runStrategy` 时仍检测运行状态，但发现停止后提示手动启动，不消耗自动启动重试次数。缺少核心查询接口时给出具体缺失项，不假装在线或离线。

检测到 QMT 仍报告模型运行时，即使 Pipe 通道暂时失联也不会重复启动。调用启动接口只记为“已提交启动”；桥接是否正常由独立的 Pipe 状态确认。

恢复不会修改或绕过 QMT 的 IP 白名单。支持就绪查询的版本明确返回未就绪时等待；缺少独立查询的旧版本交由 QMT 自身的原生启动流程处理。如果启动后再次被 QMT 停止，按 60、120、240、300 秒退避，同一进程、同一部署代次最多尝试 5 次。达到上限后需检查 QMT 提示；QMT 重启或新部署开始新的尝试周期，连续运行且通道正常 5 分钟后清零计数。

### 升级后的部署衔接

升级可能需要替换 QMT 内已导入的托管策略。若生成新包时旧 QMT 仍在运行，部署会等待终端退出；此时 `reimport_required=true`、模型尚未准备完成，自动恢复记录为 `ineligible`，不会启动旧部署代次的模型。

Web 自动启动、计划重启和绑定重启会在确认旧 QMT 退出后，同步完成该目录的导入队列及模型配置，再启动 QMT。此步骤不依赖后台部署线程抢到退出与启动之间的时间窗口；部署失败或模型尚未准备好时阻止启动并报告原因。新策略上线后清除代次过渡状态，恢复常规运行检测。

### 外部程序调用

Python 方法 `runtime.recover_strategy(account_id, account_type=..., bridge_id=...)` 与 HTTP `POST /api/qmt/strategies/recover` 可触发指定绑定的即时恢复检查，也可通过 `account_key` 唯一定位绑定。程序直接复用绑定时的 `RuntimeManager` 对象；本地托管实例由 SDK 自动读取管理凭据，`runtime.accounts.recover_strategy()` 也是等价入口。返回值区分已提交启动、模型已运行及通信已确认；详细用法见 [第三方项目管理 SDK](第三方项目管理SDK.md#外部程序恢复-qmt-托管策略)。

接口沿用上述生效范围、绑定校验和重试规则，与后台检测共用执行锁。导入未完成时返回 `ineligible` 和 `deployment_pending` 原因，自动运行未开启时也返回明确原因；不会通过接口跳过部署或重置失败次数。

### 非法 IP 弹窗关闭与日志

后台每秒轻量检查绑定进程的可见 Qt 消息窗，策略状态常规检查仍为每 20 秒一次。出现候选弹窗时提前检查，以免提示按倒计时自动消失后漏记。

处理 Qt 类型匹配的 `CGlobalMessageDialog` 和旧版 `CMessageBox`，通过 QObject 子控件和 `CSimpleTextWidget` 类型查找文本，不读取固定的私有成员偏移，也不校验 `Dialog.dll`、`BaseWidget.dll` 整文件哈希。正文必须完整匹配“[防外接] Python进程访问了网络地址 […]，策略运行中止！”或旧版“非法IP:192.0.2.1:18028 198.51.100.2:59782”格式，且只能找到一个匹配文本。旧版地址列表逐项校验 IPv4 和可选端口。读取、关闭前再次核对绑定和正文，其他消息不关闭。缺少消息读取、关闭接口时，仅对应功能不可用；可选消息扫描失败会记录 `notice_error`，策略运行检测继续。

处理时先记录告警原文。`CGlobalMessageDialog` 调用自身的 `closeMessage`；旧版 `CMessageBox` 查找该窗口内唯一可见、可用的“确定”或“OK”按钮，在 Qt GUI 线程调用按钮的原生 `click()`，不模拟鼠标点击，不改变“不再提示”选项。两类关闭接口分别检测能力，旧版按钮不依赖 `closeMessage`。按钮缺失、禁用或存在歧义时保留警告；调用后确认窗口已隐藏或销毁。即使策略已经恢复运行，也仍会检查并关闭符合条件的告警。只有窗口确认关闭、绑定模型确认运行，并且独立 Pipe 查询确认进程、角色、部署代次及通信状态均正确后，才记录“非法 IP 弹窗已关闭，绑定策略及通信恢复成功”。

日志按本机日期追加到 `runtime/logs/qmt_strategy_recovery/YYYY-MM-DD.jsonl`，采用 UTF-8，一行一个 JSON 事件。包含带时区的时间、账号、模式、QMT PID、部署代次、告警原文和关联事件编号 `event_id`。主要事件为：

| 事件 | 含义 |
| --- | --- |
| `illegal_ip_detected` | 发现并记录非法 IP 告警 |
| `illegal_ip_popup_result` | 关闭结果，`closed=true` 表示确认已隐藏 |
| `strategy_start_requested` | 已提交绑定策略启动 |
| `illegal_ip_handled` | 弹窗关闭、策略和通信恢复均已确认 |
| `illegal_ip_processing_failed` | 处理异常，记录错误原因 |
| `illegal_ip_recovery_pending` | 退避等待或重试次数已耗尽 |

日志会在关闭前刷新到磁盘；如果告警日志无法写入，保留弹窗并在状态文件记录错误。策略启动请求本身不算处理成功，通信尚未确认时继续等待。重启检测器时从状态文件恢复事件进度，已完成事件不重复记成功。

2026-11-04，在指定的国金模拟账号上验证当前 Lite 托管策略：

1. 原生查询确认模型运行，使用策略管理方法停止该模型后，查询确认已停止。
2. 自动恢复控制器检测停止并调用原生启动方法。
3. 模型重新运行，Pipe 返回同一 QMT 进程、当前部署代次和 `running` 状态。
4. 再次检测不重复启动。向原生启动入口传入错误的模型 ID、账号、模式、名称、账号 Key 均被拒绝。

后续加入弹窗关闭和日志后，再次在同一模拟账号验证：直接恢复控制器约 1.28 秒完成；后台独立运行时约 2.16 秒完成“发现告警 → 原生关闭 → 启动绑定模型 → 独立通信确认 → 成功日志落盘”。测试生成的真实非法 IP 警告窗口已经隐藏，事件关联完整。

这些实测没有下单，未操作其他终端。

同日补充验证了 QMT 的真实非法 IP 处理入口：向 `CStrategyTradeManager::onIllegalIPFind` 注入测试地址 `192.0.2.1`，没有实际创建外网连接。QMT 自己执行了停策略及告警流程，显示“[防外接] Python进程访问了网络地址 [192.0.2.1]，策略运行中止！”。后台检测自动恢复模型，独立 Pipe 查询确认通道恢复，本轮共约 14.46 秒。

另一次在告警窗口仍可见时立即执行相同的恢复控制器：策略启动成功，约 1.91 秒内确认 Pipe 正常，确认时告警仍可见。没有关闭提示或模拟鼠标点击。该构建的提示为 `XP::CGlobalMessageDialog` 消息窗，会按界面倒计时自动消失，不阻塞原生策略启动。

从本地二进制调用链确认，非法 IP 的处理顺序是：

1. `onIllegalIPFind` 调用 `stopAllStrategy`，停止该 QMT 实例中的全部模型。
2. 将地址加入当前告警集合并记录日志；若本次确实停止了运行中的模型，汇总地址并发送 `sigFindIllegalIP`。
3. `CHomePageTradeWidget::slotFindIllegalIP` 生成警告文案，经 `CMsgService::showMsg` 显示。
4. cfquant 恢复控制器重新核对绑定，仅启动当前绑定模式的托管模型；其他模型不由本控制器恢复。

以上验证覆盖“已判定非法 IP 后”的真实处理链，未覆盖外部请求如何被判定非法，也未证明早晨的实际地址属于讯投官网。实际白名单及网络监测规则没有修改，告警来源仍需要真实现场的地址和网络记录确认。

## 查看状态与单账号验证

Web 服务启动后运行内置恢复线程，状态写入 `runtime/status/qmt_strategy_recovery.json`，绑定接口的 `qmt_strategy_deploy.targets[].recovery` 也会返回结果。该线程独立于 Pipe 控制线程，等待 Qt 界面不会阻塞通道同步。Frida 附加与原生方法在独立子进程中执行；异常退出或超时会记录 `unavailable`，Web 和 Pipe 控制继续运行，原生操作结果不确定时不自动重放。原生子进程故障至少间隔 60 秒重试，可见弹窗不会绕过这一退避。

兼容依赖固定为 `frida==17.16.4`。设置 `CFQUANT_QMT_AUTOMATION=0` 可关闭原生恢复和组件登录，改为手动操作；安装与关闭方式见 [QMT 组件登录工具](QMT组件登录验证.md)。

### Frida 文件与写盘控制

恢复检测复用一个独立 Frida 工作进程，在多个绑定、后续轮询之间共用 DLL 缓存。每轮检查结束仍会释放对应 QMT 会话及登录互斥锁；下一轮重新读取当前进程和绑定，不使用过期模型状态。工作进程崩溃或超时后终止本次操作，不自动重放，后续检测按原有退避重建进程。

当前兼容版本在 Windows 上首次使用仍需释放约 45 MB 的代理 DLL。持续轮询复用这些文件，避免每 20 秒重复写入；Frida 原始标准输出和错误输出通过内存管道消费，不额外保存日志。策略恢复告警仍保留原有事件日志。

临时文件位于项目安装目录或解压目录下的 `runtime/frida/worker-*`；管理 SDK 设置了 `home` 时使用该目录下的 `runtime/frida`。支持 `CFQUANT_RUNTIME_DIR`，也可单独用 `CFQUANT_FRIDA_TEMP_DIR` 指定位置。仅子进程的 `TEMP/TMP/TMPDIR` 指向专用目录，不更改系统临时目录；目录不可写时报告失败，不退回 C 盘系统临时目录。

正常退出先释放 QMT 会话，再调用 `frida.shutdown()`，父进程随后清理该工作目录。异常退出也由父进程清理；已停止工作进程的遗留目录在后续创建或轮询时回收，文件暂时占用则保留所有权记录后重试。回收只处理自身标记的目录，核对进程创建时间，不删除仍在使用的目录，也不遍历目录链接。

使用真实 Frida 17.16.4 对两个一次性测试进程交替执行 20 轮检查：首次释放 9 个 DLL、合计 45,288,936 字节，后续没有重复 DLL 写入；正常退出及模拟崩溃后的残留均为 0，C 盘系统临时目录未新增 Frida 目录。此验证不操作实际 QMT 策略。

命令行默认只检查：

```powershell
python -m cfquant.qmt_strategy_recovery --account-id YOUR_ACCOUNT
```

单次检测并恢复：

```powershell
python -m cfquant.qmt_strategy_recovery --account-id YOUR_ACCOUNT --ensure
```

持续检测指定账号：

```powershell
python -m cfquant.qmt_strategy_recovery --account-id YOUR_ACCOUNT --watch --report runtime/status/qmt_strategy_watch.json
```

独立检测器每轮重新读取绑定及部署配置，不写回这些配置。`--parent-pid WEB_PID` 可将临时检测器生命周期绑定到当前 Web 进程，Web 退出后检测器退出，由下一次启动的内置线程接管。不要为同一账号额外启动多个独立检测器。
