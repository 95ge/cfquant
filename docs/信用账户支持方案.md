# 信用账户支持方案

更新时间：2026-08-18
状态：第一阶段已实现，信用专项交易动作待券商 QMT 常量验证

## 0. 当前落地状态

已完成：

- 网页账号绑定、初始化向导、首页账号下拉和接口调试支持选择 `STOCK` / `CREDIT`。
- 后端账号配置升级为 `account_key = bridge_id:account_type:account_id`，兼容历史只按 `account_id` 保存的配置。
- 资产、持仓、委托、成交、下单、撤单、回调订阅和回调历史拉取均已贯通 `account_type`。
- 通用模式 ctypes 和高级模式 LTtx 均可按账号配置自动路由；高级模式不可用时仍按原逻辑回退通用模式。
- 新增 `POST /api/credit/query`，支持 `query_credit_detail`、`query_credit_subjects`、`query_credit_slo_code`、`query_credit_assure`、`query_stk_compacts`。
- 新增 `POST /api/credit/probe`，用于只读探测当前 QMT 对信用账户基础查询和信用专项查询的支持情况。

暂未直接开放：

- 融资买入、融券卖出、买券还券、卖券还款、现券还券等信用专项委托动作。原因是不同券商 QMT 的 `passorder` 常量和业务动作可能不一致，需要先在当前券商环境完成小额委托和撤单验证。

## 1. 背景和目标

当前系统默认按普通证券账户运行，核心能力已经覆盖通用模式 ctypes、高级模式 LTtx/QMT、网页端账号绑定、交易查询、委托、撤单、行情和数据下载。

信用账户接入不建议设计成独立通信模式，而应作为账号类型接入现有账号绑定和路由体系。也就是说：

- 通信模式仍然是通用模式或高级模式。
- 账号维度增加 `account_type=CREDIT`。
- 外部 Python 使用方式尽量保持 xtquant 风格，例如 `StockAccount("8885060548", "CREDIT")`。
- 网页端账号绑定、首页账号选择、接口调试、交易面板都能识别普通账户和信用账户。

目标是让用户可以在同一套系统中同时管理普通账户和信用账户，并且在多账号场景下按账号类型准确路由到对应 QMT 部署端。

## 2. 当前项目已有基础

从现有代码看，系统已经具备一部分信用账户基础：

- `cfquant/xtconstant.py` 已有 `CREDIT_ACCOUNT = 3`，并在账户类型字典中映射为 `CREDIT`。
- `cfquant/xttype.py` 的 `StockAccount(account_id, account_type="STOCK", bridge_id=None)` 已支持传入 `CREDIT`。
- `cfquant/xttrader.py` 已存在信用账户相关兼容方法：
  - `query_credit_detail`
  - `query_credit_subjects`
  - `query_credit_slo_code`
  - `query_credit_assure`
  - `query_stk_compacts`
- `cfquant/tx_trade_bridge.py` 已为上述信用查询方法配置了 QMT 候选调用名。
- 当前网页服务里仍有多处默认写死 `account_type=STOCK`，因此网页端还没有真正完成信用账户适配。

结论：底层模型和一部分兼容接口已经有雏形，主要缺口在网页配置、账号路由、交易动作语义和真实 QMT 能力验证。

## 3. 设计原则

1. 信用账户是账号属性，不是新的部署模式。

   通用模式和高级模式都应该能承载信用账户，只是底层 QMT 是否支持某个信用接口，需要通过能力探测确认。

2. 普通账户和信用账户共享一套外部接口风格。

   外部用户仍然使用 `cfquant.xttrader`、`cfquant.xtdata`、网页 API，不需要理解底层是 ctypes、LTtx 还是 pipehub。

3. 信用交易动作必须显式化。

   信用账户不能只用普通的 `buy/sell` 模糊表达，因为信用账户存在担保品买入、担保品卖出、融资买入、融券卖出、买券还券、卖券还款、现券还券等业务动作。

4. 先查询，后交易。

   第一阶段优先接入资产、持仓、委托、成交、负债、合约、可融券标的等查询能力。信用交易委托应在确认 QMT 真实常量和券商行为后再开放。

5. 多账号路由必须包含账号类型。

   如果同一个资金号可能同时存在普通和信用身份，内部路由键不能只使用 `account_id`，应至少使用 `(account_id, account_type)`。

## 4. 账号绑定设计

账号绑定配置建议增加字段：

```json
{
  "account_id": "8885060548",
  "account_type": "STOCK",
  "display_name": "默认普通账户",
  "bridge_id": "default",
  "mode": "normal",
  "qmt_dir": "D:\\国金证券QMT交易端",
  "python_dir": "D:\\国金证券QMT交易端\\bin.x64\\python"
}
```

信用账户示例：

```json
{
  "account_id": "8885060548",
  "account_type": "CREDIT",
  "display_name": "默认信用账户",
  "bridge_id": "credit_01",
  "mode": "normal",
  "qmt_dir": "D:\\国金证券QMT交易端_信用",
  "python_dir": "D:\\国金证券QMT交易端_信用\\bin.x64\\python"
}
```

绑定规则建议：

- 单账号默认仍为普通账户 `STOCK`。
- 添加账号时让用户选择账户类型：普通证券账户、信用账户。
- 普通账户和信用账户的 `account_id` 一般不同，但系统不能依赖这一点；内部唯一标识应使用 `(account_id, account_type, bridge_id)`，避免两个账户资金号相同或用户手工配置相同资金号时路由错乱。
- 如果用户只部署一个 QMT 且该 QMT 能访问信用账户，则普通和信用可以绑定到同一个 `bridge_id`。
- 如果普通和信用分别在不同 QMT 目录中启动，则分别配置不同 `bridge_id`。
- 首页账号下拉框显示为：`8885060548 / 普通`、`8885060548 / 信用`。

### 4.1 一个 QMT 实例承载多个普通和信用账户

需要支持一种更常见的券商柜台场景：一个 QMT 客户端里同时登录或可访问多个普通账户、多个信用账户。

示例：

- 普通账户：`8885060886`
- 普通账户：`8885060775`
- 信用账户：`1885060886`
- 信用账户：`1885060775`

这种情况下，不能再把一个 `bridge_id` 理解成一个账号。更合理的模型是：

```text
QMT 实例 bridge_id=qmt_guojin_main
  ├─ STOCK  / 8885060886
  ├─ STOCK  / 8885060775
  ├─ CREDIT / 1885060886
  └─ CREDIT / 1885060775
```

也就是说：

- `bridge_id` 表示一个 QMT 运行实例。
- `account_id + account_type` 表示这个 QMT 实例下的一个交易账户。
- 请求路由时先确定账户绑定，再根据绑定找到对应 `bridge_id`。
- 同一个 `bridge_id` 下可以挂多个账户。

推荐配置结构从“账号列表”升级为“QMT 实例 + 账户列表”：

```json
{
  "qmt_instances": [
    {
      "bridge_id": "qmt_guojin_main",
      "display_name": "国金主交易端",
      "mode": "normal",
      "qmt_dir": "D:\\国金证券QMT交易端",
      "python_dir": "D:\\国金证券QMT交易端\\bin.x64\\python",
      "data_provider": true,
      "accounts": [
        {
          "account_id": "8885060886",
          "account_type": "STOCK",
          "display_name": "普通账户 0886"
        },
        {
          "account_id": "8885060775",
          "account_type": "STOCK",
          "display_name": "普通账户 0775"
        },
        {
          "account_id": "1885060886",
          "account_type": "CREDIT",
          "display_name": "信用账户 0886"
        },
        {
          "account_id": "1885060775",
          "account_type": "CREDIT",
          "display_name": "信用账户 0775"
        }
      ]
    }
  ]
}
```

为了兼容旧配置，系统内部可以继续维护扁平账号绑定表，但生成时必须带上 `bridge_id`：

```json
[
  {
    "account_key": "qmt_guojin_main:STOCK:8885060886",
    "bridge_id": "qmt_guojin_main",
    "account_id": "8885060886",
    "account_type": "STOCK"
  },
  {
    "account_key": "qmt_guojin_main:CREDIT:1885060886",
    "bridge_id": "qmt_guojin_main",
    "account_id": "1885060886",
    "account_type": "CREDIT"
  }
]
```

这里的 `account_key` 是系统内部唯一键，不直接暴露给普通用户。

### 4.2 网页交互设计

网页绑定建议分两步：

1. 添加 QMT 实例。

   用户填写 QMT 目录、Python 目录、运行模式、实例名称。系统自动生成或允许用户填写 `bridge_id`。

2. 在该 QMT 实例下添加账户。

   用户填写资金账号，选择账户类型。一个 QMT 实例下可以连续添加多个普通账户和信用账户。

首页账号下拉框按 QMT 实例分组：

```text
国金主交易端
  普通账户 0886 / 8885060886
  普通账户 0775 / 8885060775
  信用账户 0886 / 1885060886
  信用账户 0775 / 1885060775
```

用户选择某个账户后，系统内部同时确定：

- `bridge_id`
- `account_id`
- `account_type`
- 当前模式
- 是否为数据提供端

### 4.3 QMT 侧身份上报

QMT 入口启动时不应该只上报一个默认账号，而应上报该实例身份和可服务账户列表。

建议启动心跳或状态返回中包含：

```json
{
  "bridge_id": "qmt_guojin_main",
  "qmt_dir": "D:\\国金证券QMT交易端",
  "mode": "normal",
  "accounts": [
    {
      "account_id": "8885060886",
      "account_type": "STOCK"
    },
    {
      "account_id": "8885060775",
      "account_type": "STOCK"
    },
    {
      "account_id": "1885060886",
      "account_type": "CREDIT"
    },
    {
      "account_id": "1885060775",
      "account_type": "CREDIT"
    }
  ]
}
```

账号列表的来源建议以网页配置为准，QMT 侧自动发现能力作为辅助校验。原因是不同 QMT 版本和券商环境下，自动枚举账户的接口不一定稳定。

## 5. 外部 Python 接口设计

保持当前风格：

```python
from cfquant.xttype import StockAccount
from cfquant.xttrader import XtQuantTrader

trader = XtQuantTrader()

stock_account = StockAccount("8885060548", "STOCK")
credit_account = StockAccount("8885060548", "CREDIT")

asset = trader.query_stock_asset(credit_account)
positions = trader.query_stock_positions(credit_account)
credit_detail = trader.query_credit_detail(credit_account)
```

外部调用者不需要手工指定通道。系统内部根据账号绑定关系自动选择：

- 优先使用该账号配置的高级模式。
- 高级模式不可用时回退到通用模式。
- 如果只部署通用模式，则直接走 ctypes 通用端。

## 6. 网页端需要调整的地方

### 6.1 账号绑定

新增账户类型选择：

- 普通证券账户
- 信用账户

保存时必须持久化 `account_type`。历史配置没有该字段时，迁移默认值为 `STOCK`。

### 6.2 首页账号选择

首页不再只显示资金账号，应显示账号和类型。

示例：

- `8885060548 / 普通`
- `8885060548 / 信用`

用户选择信用账户后，后续资产、持仓、委托、成交、撤单、接口调试都默认带上 `account_type=CREDIT`。

### 6.3 接口调试

接口调试页增加信用账户能力分组：

- 信用资产信息
- 融资融券明细
- 可融券标的
- 担保品信息
- 合约负债

每个接口显示：

- 是否支持
- 当前通道
- 延迟
- 原始返回摘要
- 错误原因

### 6.4 交易面板

普通账户仍显示买入、卖出。

信用账户不建议直接沿用普通买入、卖出按钮，应增加信用交易动作选择：

- 担保品买入
- 担保品卖出
- 融资买入
- 融券卖出
- 买券还券
- 卖券还款
- 现券还券

第一阶段可以只开放查询；信用交易按钮先置灰并显示“需要完成券商 QMT 常量验证后启用”。

## 7. 后端 API 设计

现有账号、查询、交易 API 需要统一增加 `account_type`。

建议请求参数：

```json
{
  "account_id": "8885060548",
  "account_type": "CREDIT"
}
```

普通账户不传时默认：

```json
{
  "account_type": "STOCK"
}
```

新增信用查询 API 可采用两种方式。

方案 A：独立接口：

```text
POST /api/credit/query_detail
POST /api/credit/query_subjects
POST /api/credit/query_slo_code
POST /api/credit/query_assure
POST /api/credit/query_compacts
```

方案 B：统一动作接口：

```text
POST /api/credit/query
```

请求：

```json
{
  "account_id": "8885060548",
  "account_type": "CREDIT",
  "action": "query_credit_detail"
}
```

更推荐方案 B，后续扩展信用接口更方便。

## 8. 通道和路由设计

内部路由建议从：

```text
account_id -> bridge_id
```

升级为：

```text
(bridge_id, account_id, account_type) -> account_key
account_key -> bridge_id
```

这样可以处理以下情况：

1. 同一个 QMT 同时承载普通账户和信用账户。
2. 普通账户和信用账户分别部署在不同 QMT 目录。
3. 多个信用账户同时运行。
4. 高级模式不可用时回退到通用模式。

通用模式 ctypes 本身不需要通过 LTtx 通信，但网页服务可以通过账号绑定关系知道哪个 `bridge_id` 对应哪个 QMT 端。多个 ctypes 通用端同时运行时，仍然需要启动参数或配置文件提供身份，例如：

```text
bridge_id=qmt_guojin_main
accounts=STOCK:8885060886,STOCK:8885060775,CREDIT:1885060886,CREDIT:1885060775
pipe_name=cfquant.credit_01.request
```

请求发送时必须明确带上目标账户：

```json
{
  "bridge_id": "qmt_guojin_main",
  "account_id": "1885060886",
  "account_type": "CREDIT",
  "action": "xttrader.query_stock_asset"
}
```

回调和订阅路由也要升级。当前如果只按 `bridge_id + account_id` 订阅，遇到资金号相同但账户类型不同的情况会有歧义。建议统一改为：

```text
bridge_id + account_type + account_id + client_id
```

行情回调通常不属于某个交易账户，可按 `bridge_id` 或数据提供实例转发。交易回调、委托回报、成交回报、账号状态变化必须尽量带上 `account_type`。如果 QMT 原始回调无法提供账户类型，则系统需要通过账户绑定表尝试推断；如果同一 `bridge_id` 下同一个 `account_id` 同时绑定了普通和信用，则必须标记为歧义，不做静默错误路由。

## 9. QMT 策略入口文件设计

引入信用账户后，原则上不需要为信用账户复制一套全新的通信实现。更推荐复用现有 QMT 入口文件，通过不同的运行身份区分实例。

现有入口文件：

- `qmt_scripts/CFQUANT_CTYPE_ALL_LOWLAT.py`：通用模式入口，同时承载查询、交易和行情。
- `qmt_scripts/CFQUANT.py`：高级模式普通 QMT 入口。
- `qmt_scripts/CFQUANT_TRADE_LOWLAT.py`：高级模式极速交易 QMT 入口。

推荐规则：

1. 单 QMT、单账号或一个 QMT 同时可访问多个普通和信用账户时，不需要新增信用专用入口文件。

   用户仍然加载 `CFQUANT_CTYPE_ALL_LOWLAT.py`，网页绑定中在同一个 QMT 实例下配置多个普通账户和信用账户即可。系统通过请求里的 `account_id` 和 `account_type` 调用对应账户能力。

2. 多 QMT、多账号或普通和信用分别部署在不同 QMT 目录时，每个 QMT 实例都需要一个独立运行身份。

   这里不建议复制多份核心入口代码，而是让同一个入口读取不同配置，例如：

   ```text
   CFQUANT_BRIDGE_ID=credit_01
   CFQUANT_ACCOUNTS=STOCK:8885060886,STOCK:8885060775,CREDIT:1885060886,CREDIT:1885060775
   ```

   或者由网页为每个账号生成独立运行配置文件，再由同一个 QMT 入口自动读取。

3. 为了降低部署成本，可以提供轻量级“启动入口模板”。

   例如未来可以在 `qmt_scripts` 增加非常薄的一层模板：

   ```text
   CFQUANT_CTYPE_ENTRY.py
   ```

   这个文件只负责读取网页生成的账号身份配置，然后启动通用桥，不复制核心桥接逻辑。

4. 高级模式仍然遵守原有部署结构。

   高级模式不是因为信用账户而增加新入口，而是因为高级模式本身需要普通 QMT 端和极速交易 QMT 端分离。信用账户只是在这两个端里增加 `account_type=CREDIT` 的路由和调用能力。

结论：信用账户和多普通账户都需要“独立账号身份”，不一定需要“独立入口文件”。真正需要区分的是 QMT 实例身份 `bridge_id`，以及该实例下的 `account_id + account_type`。

## 10. 信用交易委托设计

信用账户交易不能简单复用普通账户的 `buy/sell` 语义。

建议增加统一字段：

```json
{
  "account_id": "8885060548",
  "account_type": "CREDIT",
  "credit_action": "margin_buy",
  "stock_code": "000001.SZ",
  "price": 11.1,
  "volume": 100
}
```

候选动作：

| credit_action | 含义 |
| --- | --- |
| collateral_buy | 担保品买入 |
| collateral_sell | 担保品卖出 |
| margin_buy | 融资买入 |
| short_sell | 融券卖出 |
| buy_to_repay | 买券还券 |
| sell_to_repay | 卖券还款 |
| direct_repay_stock | 现券还券 |

需要注意：

- 不同券商 QMT 对信用交易的 `order_type`、`qmt_order_type`、`passorder` 参数可能存在差异。
- 不能在未验证常量前直接开放真实下单。
- 网页端真实信用委托必须显示账户类型、交易动作、标的、价格、数量和风险确认。

## 11. 能力探测

建议增加信用账户能力探测。

探测项：

- 当前 QMT 是否能识别 `CREDIT` 账户类型。
- `query_stock_asset(CREDIT)` 是否可用。
- `query_stock_positions(CREDIT)` 是否可用。
- `query_stock_orders(CREDIT)` 是否可用。
- `query_stock_trades(CREDIT)` 是否可用。
- `query_credit_detail` 是否可用。
- `query_credit_subjects` 是否可用。
- `query_credit_slo_code` 是否可用。
- `query_credit_assure` 是否可用。
- `query_stk_compacts` 是否可用。

探测结果保存到网页状态中，示例：

```json
{
  "account_id": "8885060548",
  "account_type": "CREDIT",
  "bridge_id": "credit_01",
  "capabilities": {
    "asset": true,
    "positions": true,
    "orders": true,
    "trades": true,
    "credit_detail": true,
    "credit_subjects": false,
    "credit_slo_code": true,
    "credit_assure": true,
    "stk_compacts": true
  }
}
```

网页端根据信用能力探测结果决定显示、隐藏或置灰对应功能。

## 12. 实施阶段

### 阶段 1：账号类型贯通

- 账号绑定增加 `account_type`。
- 后端 API 支持 `account_type` 参数。
- 首页账号下拉框显示账户类型。
- 所有查询、委托、撤单请求都带上账户类型。
- 历史配置默认迁移为普通账户。

### 阶段 2：信用查询接入

- 接入 `query_credit_detail`。
- 接入 `query_credit_subjects`。
- 接入 `query_credit_slo_code`。
- 接入 `query_credit_assure`。
- 接入 `query_stk_compacts`。
- 网页端增加信用查询调试区。

### 阶段 3：信用能力探测

- 新增信用账户探测接口。
- 探测结果写入运行状态。
- 网页端按能力显示功能。
- 文档标注当前券商 QMT 实测支持情况。

### 阶段 4：信用交易动作

- 梳理当前券商 QMT 的信用交易常量。
- 对担保品买入、担保品卖出先做小额真实委托和撤单验证。
- 验证融资买入、融券卖出、买券还券、卖券还款等动作。
- 网页端开放信用交易动作选择和风险确认。

### 阶段 5：多账号和故障回退

- 支持普通账户和信用账户分别绑定不同 `bridge_id`。
- 高级模式不可用时自动回退通用模式。
- 数据提供商账号失效时，自动切换到可用账号。
- 信用账户下线时，网页端明确提示“信用账户通道不可用”，不影响普通账户。

## 13. 需要确认的问题

1. 当前券商 QMT 版本中，信用查询函数的真实函数名和参数是否与兼容候选一致。
2. 信用账户在 QMT 中是否与普通账户使用同一个资金号，还是独立资金号。
3. 当前 QMT 是否允许一个终端同时访问普通账户和信用账户。
4. 信用交易各业务动作对应的 `qmt_order_type` 和 `order_type` 常量。
5. 高级模式两个 QMT 端是否都需要支持信用账户，还是只在通用模式中先支持信用。
6. 网页端是否默认隐藏信用交易入口，只保留信用查询入口。

## 14. 推荐落地路径

建议先做“只读信用账户支持”：

1. 先把 `account_type` 从网页配置贯通到后端 API 和桥接层。
2. 先验证信用账户资产、持仓、委托、成交查询。
3. 再接入信用专用查询接口。
4. 最后再开放信用交易动作。

这样风险最小，也最容易判断当前 QMT 版本和券商环境到底支持哪些信用能力。
